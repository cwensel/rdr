# Stage 7.1 — Cluster Reconcile (cross-RDR drift)

> **Run once per CLUSTER, not per RDR. Most RDRs skip this** — it fires only
> when a *cluster* of related RDRs is **all Final and none yet Implemented**.
> A solo RDR goes Stage 7 → (skip 7.1) → Stage 8. The `7.1` number means
> "between Finalize (7) and Implement (8)"; it is **not** a substep of Finalize
> and it is **not** in the per-RDR spine.

**Goal**: close cross-RDR drift before any RDR in the cluster is implemented —
the one defect class no per-RDR gate covers, because a per-RDR Pairwise compares
an RDR only to peers that *already exist*, never an earlier peer against a later
lock.

## Why a gate, not a per-RDR step

Cross-spec consistency is **not** gated on each spec being internally finished
first — viewpoints are checked "between particular parts… and at particular
stages, rather than enforced as a matter of course" (Finkelstein et al. 1994),
and inconsistency may be "delayed indefinitely" (Easterbrook 1994). So the flow
*tolerates* cross-RDR inconsistency during per-RDR work and reconciles it once,
at cluster granularity — paying the cost Easterbrook names (tolerated
inconsistencies "may accumulate") at a single planned stop rather than
re-checking every pair on every lock.

## When it fires

A cluster of related RDRs is **Final and none yet Implemented** — the window
where the set is frozen but still the authority (no code yet), so a
contradiction between two locked peers is a *spec* question. Once **Implemented,
code is the source of truth**, so later drift is out of scope. "Related" = RDRs
that name each other as `**Predecessors**:`, cite each other (Method: Peer RDR),
or share a Cross-Cutting Concern; an RDR with no such peer skips this gate.

## Paste this

Fill `{RDR_RECORDS}` (the cluster's RDR directory) and the peer pairs to compare.
This gate is per-cluster (no single `<rdr-slug>`), so its output goes under the
cluster `{EVIDENCE_DIR}` — the prompt below binds it, and the seam, and lists
what lands there.

**Prompt**: [`../prompts/stages/07.1-cluster-reconcile.prompt.md`](../prompts/stages/07.1-cluster-reconcile.prompt.md)
— it owns the iteration contract (step 2's scoping of step 3) and the four
dispositions; the `/rdr-cluster-reconcile` skill runs it. Paste its body by hand
if driving without the skill.

```text
Reconcile cross-RDR drift across the cluster of related RDRs under {RDR_RECORDS}
that are Final-and-unimplemented, before any of them is implemented. Step 2's
prompt binds {RDR_RESOURCES} (corpora/design docs) and {EVIDENCE_DIR}.

1. Build the cluster.
   `"$RDR_HOME/bin/recs" index --json --cluster-of <NNNN> --closure --final-unimplemented`
   is the membership (mutual Predecessors, Peer-RDR citations, shared
   Cross-Cutting Concerns and declared `Cluster` fields, to a fixpoint):
   `cluster[]` is the set, each member carrying the relation that earned it
   and `via`; `out_of_scope[]` is the record of what was dropped and why
   (`not-final`, `impl-complete`, `candidate`). A `candidate` is confirmed
   (re-run with it added to the seeds: `--cluster-of A,B`) or dismissed,
   never expanded. A member the records never cite is declared in the
   `Cluster` field, not inferred here.

2. Bind the ITERATION CONTRACT, which scopes step 3 below; every finding step 3
   returns is then forced into one of its four DISPOSITIONS. Mechanics: the
   prompt ../prompts/stages/07.1-cluster-reconcile.prompt.md enforces both —
   read it, don't re-derive them.

3. Run the set-scoped checks (at N>1, only those step 2's iteration contract
   leaves in scope):
   - Whole-RDR-set Critique — the higher-leverage variant in
     ../prompts/pre-lock/2-critique.md (whole-set prompt). Names the most likely
     INTER-RDR failure mode, the one RDR most likely rewritten, the
     cross-cutting assumption that won't survive.
   - Pairwise Contradiction Scan — ../prompts/gate/pairwise.md, run for
     every plausibly-interacting pair (trim to pairs named in a Critical
     Assumption Method: Peer RDR or a Cross-Cutting Concern). For any pair that
     declares a Round-Trip / Inverse Invariant (one emits, the other re-pairs /
     reconstructs), the scan must assert that invariant holds across the seam
     byte-/value-for-byte — not merely that the two signatures agree. This is
     the one cross-RDR check no per-RDR lens can run.
   Delegate the heavy reads (reading several RDRs, running the pairwise prompt
   per pair) to a sub-agent that returns the findings table, not the RDR text.

HARD RULE — a cross-RDR contradiction is never absorbed as a wording tweak to
the DESIGN BODY of a Final RDR. The frozen content is what's protected; the flip
to Draft (status + README row + re-entry note) is the act that lifts the freeze,
not a forbidden edit. (Final → Draft is the same backward edge Stage 7 uses for
an implementation-time spec defect; this gate just finds it earlier.) A
JOINT-DECISION tolerance makes no design-body edit either — the decision's text
lives at its home, cited not restated, and the sibling gains only the Status
qualifier — so the rule is not in play on that path.

Output (written to `reconcile-report.md`):
  - Iteration N, each member's revision as examined, and each joint-decision
    home's — the next iteration reads the home revisions to see what answered.
  - An "Inputs run" table, one row per check (whole-set critique + every pair in
    the cluster, scanned or not): RE-SCANNED, CARRIED or TRIMMED, plus the
    scanned/possible count. A CARRIED row names the iteration its verdict comes
    from, a TRIMMED row why the pair is not plausibly-interacting — so neither a
    skipped scan nor a dropped pair is read as a passed one.
  - A table: pair | finding TYPE | SEVERITY | disposition (NO CONFLICT /
    SPEC-DEFECT / JOINT-DECISION / CITATION REPAIR / DEFERRED) | for
    SPEC-DEFECT, which RDR returns to Draft + target stage + SCOPE
    (RE-LOCK-ONLY / STAGE-SCOPED / FULL-FLOW) + why that scope; for
    JOINT-DECISION, the home (the seam's JDR
    entry, or a declared interface) + the open question + where the tolerance is
    recorded; for CITATION REPAIR, the artifact of record and the peer text
    replaced by the citation; for DEFERRED, the RDR, the mechanical check that
    decides it, and which of the three conditions carried it. DEFERRED rows from
    prior iterations are restated here — that restatement is what catches a
    repeat.
  - Verdict: RECONCILED (no SPEC-DEFECT) — the cluster may implement; list any
            deferred items with their checks.
            RECONCILED WITH TOLERANCES — no SPEC-DEFECT stands open; list each
            standing tolerance (pair, joint decision, home, open question) and
            whether the home has answered it, alongside any deferred items. The
            cluster may implement; a sibling with an ANSWERED tolerance runs its
            scoped check first.
            NOT RECONCILED — list each SPEC-DEFECT, the RDR demoted to Draft,
            and the stage + SCOPE it re-enters at.
            STOPPED (`models/rdr-loop.toml --outcome cluster-cap` answered
            `stopped:cluster-flapping`: past the cap with entries open) — emit
            it instead of demoting; the report carries the open entries and the
            decomposition question, and the cluster waits on §strong-consult
            then the author.
  - For each SPEC-DEFECT: the demoted RDR is left flipped to the qualified Draft
    (`Draft [revised from Final …; re-verify …]`, README row updated) with its
    re-entry note appended — done, not merely recommended.
  - For each JOINT-DECISION: the decision is hoisted to its named home and each
    sibling's Status carries the tolerance qualifier — done, not merely
    recommended.
  - For each DEFERRED item: the entry is written into the affected RDR's
    `<art>/deviations.md` with its check — done, not merely recommended.
```

## Re-entry scope — re-run a stage, or re-run the flow?

A demotion names a target stage; it must ALSO name how far forward to re-walk,
because the cascade re-opens every gate downstream of the entry stage. That
scope sets the cost, so it is the report's call, sized to the defect — its
`re-verify <IDs>` set *is* the blast-radius signal. Default DOWN this table:

| Scope | When (`re-verify` set) | Re-walks |
| --- | --- | --- |
| **RE-LOCK-ONLY** | `none` — wording / cross-ref, no assumption disturbed | the fix, then Stage 7 re-locks (no round re-runs) |
| **STAGE-SCOPED** | a bounded set — specific assumptions or a contained slice change, approach holds | re-enter at Stage 3 or 4, forward through 6 → 7 |
| **FULL-FLOW** | the **chosen approach** or a foundational assumption is voided | the full 2 → 7 cascade |

Pick the narrowest scope that covers the blast radius; escalate to FULL-FLOW
only when a narrower one would re-lock over an un-re-examined contradiction, and
say so in one line (e.g. "voids 0034's merge strategy — premortem + downstream
lenses stale"). Re-walking gates the defect didn't touch buys cost, not defect
yield (Porter 1998).

**Run when**: ≥2 related RDRs are Final and none yet Implemented — typically
the moment before you start implementing the first one. **Produces**: the
whole-set Critique + Pairwise findings and the per-iteration
`reconcile-report.md` under `{EVIDENCE_DIR}`; any demoted RDR
already flipped to `Draft [revised from Final …; re-verify …]` (README row
updated) with a re-entry note carrying the full disposition inline — target
stage AND re-entry SCOPE; any tolerated sibling left Final with its
`[joint decision → <home>]` qualifier; any deferred finding written into the
affected RDR's `<art>/deviations.md`.

## Review gate

- **Is the cluster correct?** Every member Final, unimplemented, and genuinely
  related — an over-broad cluster wastes pairwise runs; a missed peer is the
  drift this gate exists to catch.
- **No SPEC-DEFECT "fixed" by editing the design body of a Final RDR.** A "we
  adjusted the wording" disposition is a process error (see the HARD RULE).
- **Was each demoted RDR actually flipped and annotated?** NOT RECONCILED must
  leave every demoted RDR in Draft (README row updated) with a re-entry note
  carrying defect + target stage + direction inline — done, not a recommendation
  — so a fresh session resumes without re-reading this report.
- **Was the right RDR demoted?** A NAMED NORMATIVE HOME OUTRANKS FOUNDATIONAL
  ORDER: where a JDR entry or an RFD principle already decides, the disagreeing record
  yields even if it is the more foundational of the two. "Less foundational
  yields" settles only pairs with no home. State which and why. Demote at all
  only for a contradiction in *meaning* between fenced normative text, where an
  implementer must choose between contracts AND a cluster principle breaks;
  where the home itself is incomplete, hoist a JOINT-DECISION paragraph rather
  than demoting on a guess.
- **Is each JOINT-DECISION genuinely joint?** A defect internal to one RDR
  dressed as a shared decision dodges a real demotion — name why neither RDR
  solely owns it, or re-run with the SPEC-DEFECT disposition.
- **Is each home a paragraph per decision, and does any sibling restate it?**
  A home whose entries carry derivation or alternatives is growing into a fourth
  peer — move that prose to the evidence tree. A sibling restating a homed
  decision's mechanism prose is a finding, repaired to a citation.
- **Does every shared census/figure have one artifact of record?** Named at the
  home, cited by peers, restated by none. A peer figure disagreeing with the
  artifact is a citation repair — typing it as a JOINT-DECISION, a demotion, or
  a deferral is the gate arbitrating a number no contract reads.
- **Does each DEFERRED item clear all three conditions?** Unfenced (or a figure
  no contract reads), decided by a named mechanical check, and changing no
  clause's meaning — with the entry actually written to `<art>/deviations.md`.
  A deferral over fenced normative text, or over two clauses that mean
  different things, is a dodged demotion; so is one whose "check" nothing runs.
  A finding matching a prior report's DEFERRED row is a SPEC-DEFECT — deferring
  it again is the gate declining to decide twice.
- **Did every member run its propose-time joint-decision check?** A member with
  no `Joint-check:` line in Decision Rationale skipped that gate item rather
  than passing it; run the check for it here (prompts/stages/02-propose.prompt.md
  step 8) against the cluster before trusting this gate's coverage.
- **Does each tolerance have a home, a question, and a record?** Every
  JOINT-DECISION names its normative home (§-anchor or declared interface) and
  each sibling carries the Status qualifier naming the open question — a
  homeless or questionless tolerance is an unmanaged contradiction; re-run.
- **Has any home answered since the last report?** Not a question to remember to
  ask — diff each home's recorded revision. For every answer that surfaces, each
  sibling holding a tolerance against it shows the scoped answer-vs-fences
  check — cleared (qualifier dropped, recorded) or raised as a SPEC-DEFECT. An
  answered tolerance still reading as a bare qualifier is the masked-defect
  case: the marker asserts a coherence the answer may already falsify.
- **Is the SCOPE the narrowest that covers the blast radius?** Each SPEC-DEFECT
  names a SCOPE consistent with its `re-verify` set, plus why. A `re-verify
  none` defect scoped above RE-LOCK-ONLY, or a contained-assumption defect
  scoped FULL-FLOW, is a cost error: a simple change must not drag a full flow
  behind it; only a voided approach or foundational assumption earns one.
- **Were both prompts run** (whole-set Critique + per-pair Pairwise), output
  under `{EVIDENCE_DIR}`?
- **At iteration N>1: is the run anchored to its history?** Every check is a
  RE-SCANNED or CARRIED row (a carry names its source iteration), the re-scans
  are exactly the pairs whose members moved, and each blocking finding traces to
  an open ledger entry. A member demoted on an unledgered finding alone is the
  plank problem — the gate is grading its own last repair; record it as net-new
  and let the ledger close.
- **Did the cap hold?** The `cluster-cap` row was resolved at entry, and a
  `stopped:cluster-flapping` answer is the report (open entries + the
  decomposition question), not a fourth demotion. Owed answer-vs-fences checks
  still run.

If NOT RECONCILED, the demoted RDR re-locks before the cluster implements,
re-walking exactly its named SCOPE and no more. Do not implement over a known
cross-RDR SPEC-DEFECT. A tolerated joint decision with a named home does not
block implement — it is typed non-defect, and the home is the authority. Nor
does a deferred item: it is typed non-defect too, and its mechanical check is
Stage 8's to run.

## Advance when

Verdict RECONCILED or RECONCILED WITH TOLERANCES: no cross-RDR SPEC-DEFECT
stands open across the cluster.
Each RDR may now proceed to [Stage 8 — Implement](08-implement.md)
independently. (If an RDR was demoted, it rejoins the cluster only after it
re-locks at its named SCOPE; re-run this gate if that rewrite touched a
cross-RDR seam — likelier under FULL-FLOW than a RE-LOCK-ONLY wording fix. A
tolerance-only outcome triggers no rewrite, so it triggers no re-run *while the
tolerance is unanswered* — the home's answer is itself a trigger: re-run this
gate scoped to the siblings holding tolerances against that question.)

**Answers land before re-locks.** A sibling whose tolerance the home has
answered runs its scoped check before it re-locks or implements. If a sibling
must re-lock first, it re-locks CARRYING the open qualifier — Stage 7's flip to
`Final` re-writes the qualifier forward, it never silently drops it.
